# Mailstream Flutter UI

A Flutter desktop front end for Mailstream (macOS, and Windows: see [Windows](#windows)), styled after macOS 26's Liquid Glass with Dia's islands. The Mailstream engine
(accounts, OAuth, sync, push, the cache, threading and AI tagging) runs inside this app's
process: `packages/mailstream` is the Dart binding of the `FFI/` crate (generated by
uniffi-dart), and its build hook bundles `libmailstream.dylib`, which holds the Rust engine (`Engine/`).
The app also carries the `mailstream` command line in `Contents/MacOS` (the Xcode build copies
`Engine/target/release/mailstream`, which `ffi.sh` builds); it starts this app when no front end runs.
The UI lists accounts, mailboxes and conversations, reads previews, sender avatars and
messages (with their HTML), searches, marks, archives, trashes, tags, replies and sends new mail through it,
does Google Chat (the spaces of every chat account, their messages, sending and starting new
chats), manages accounts and settings, and follows the engine's change events instead of polling.
Mailstream.app need not run.

```sh
# at the repository root: the release engine, command line and Dart bindings (packages/mailstream/lib/src, not committed)
CONFIG=release DART_OUT=$PWD/Flutter/packages/mailstream/lib/src ./scripts/ffi.sh
cd Flutter
flutter test                              # targeted/unit tests (header padding allows install_name rewriting)
flutter build macos --release           # build/macos/Build/Products/Release/Mailstream Flutter.app
../scripts/sign.sh "build/macos/Build/Products/Release/Mailstream Flutter.app"
```

Signing with the app's identifier and team lets the engine read the sign-ins Mailstream keeps
in the Keychain. The build is arm64 only. The app is not sandboxed.

## Windows

`windows/` is the Windows x64 runner. The same Dart UI runs there; `lib/platform.dart` (`Host`)
holds every place the two desktops differ, and the Mac's behavior is unchanged. The engine is
the same Rust one, as `mailstream.dll` beside the executable (the build hook bundles
`FFI/target/release/mailstream.dll`; its Windows specifics are in the root README's FFI section).
The built-in OAuth clients and push settings come from a `config.json` placed beside
`mailstream_ui.exe` (nothing commits or writes one); without it the app has neither, as an
unconfigured Mac build. Build on Windows with Rust (MSVC), Flutter and Visual Studio 2022's
"Desktop development with C++" workload (MSVC, the Windows SDK, C++ CMake tools):

```sh
# at the repository root, in Git Bash
CONFIG=release DART_OUT=$PWD/Flutter/packages/mailstream/lib/src ./scripts/ffi.sh
cd Flutter && flutter build windows --release   # build/windows/x64/runner/Release/mailstream_ui.exe
```

Flutter links plugins with symbolic links, which need Windows' Developer Mode; without it,
junctions made by hand in `windows/flutter/ephemeral/.plugin_symlinks` (`mklink /J <plugin>
<its folder in the pub cache>`, as `.flutter-plugins-dependencies` lists them) work too.

The GitHub Actions `Windows` workflow builds it, starts the app and keeps a screenshot and the
zipped Release folder as artifacts. On Windows:

- Window: the system title bar moves, maximizes and closes the window (`WindowDragArea` does
  nothing there, and no `macos_window_utils` call is made). The window opens at 1240×800,
  centered, titled Mailstream, no smaller than 820×520. There is no system glass under the
  Flutter view: the window is painted `MailColors.window`, and toolbar `GlassCapsule`s are
  frosted by Flutter (a backdrop blur, a translucent fill and a hairline rim) instead of the
  AppKit `mailstream/glass` view.
- Keys: every ⌘ shortcut is Ctrl (Ctrl+N, Ctrl+F, Ctrl+R, Ctrl+W, Ctrl+[, Ctrl+Enter sends,
  Ctrl+Shift+O), and Ctrl+, opens Settings, as the Mac's app menu does. Ctrl with Alt (AltGr) is
  never a command. Tooltips name the keys of the desktop they run on (`Host.shortcut`).
- Attachments: `windows/runner/window_channels.cpp` implements the `mailstream/files` channel
  the Mac's `MainFlutterWindow.swift` does: the paperclip opens the system's multi-select open
  dialog; files dragged from Explorer onto the window attach (the column shows its drop target
  while they hover); Ctrl+V attaches copied files, else copied image pixels or a screenshot
  (the clipboard's PNG, else its bitmap through WIC, written to a temporary
  `Mailstream-pasted-….png`). A clipboard holding text pastes the text, even when a picture of it
  comes along (spreadsheet cells). Folders are not attached.
- Opening attachments and links: the runner's `mailstream/shell` channel opens them with the
  shell's default verb (`ShellExecuteW`), as Explorer's double-click and the browser do.
- Chat videos play in the log through `video_player_win` (Media Foundation), the Windows
  implementation of `video_player`.
- HTML mail is not drawn yet (MS-106, which will use `webview_plus` over WebView2): a message
  with an HTML body shows its text (the engine's text part, else its HTML read as text) under a
  notice saying so (`HtmlTextFallback` in `lib/ui/reader.dart`). Links and images inside the
  HTML are therefore not shown; attachments are.

`flutter test test/windows_platform_test.dart test/compose_paste_test.dart` checks the Windows
branches on any host (`Host.debugMacOverride`): shortcut labels and bindings, AltGr, the drawn
capsule, the title bar area, the plain-text body and the Ctrl+V attachment paste.

## Application updates (macOS)

The application menu contains **Check for Updates…** and **Automatically Check for
Updates**. Sparkle 2.10.1 owns its standard consent prompt, daily scheduling, progress,
errors, authenticated installation and relaunch. Checks do not start mail sync. Automatic
downloads are off initially, system profiling is disabled, and the automatic-check preference
is Sparkle's own persisted preference (not reset on launch).

The approved production Ed25519 public key and canonical HTTPS feed are configured in
`macos/Runner/Configs/AppInfo.xcconfig`. The signed feed is published in the repository's
[`updates` prerelease](https://github.com/taooceros/mailstream/releases/tag/updates),
independently of the ad-hoc `nightly` DMGs.

Current builds explicitly opt into `prerelease` through `MAILSTREAM_UPDATE_CHANNEL`.
Sparkle accepts signed appcast items tagged `prerelease` (and ordinary stable items).
A `stable` build only accepts untagged stable items; it does not silently opt into previews.
Both use one monotonically increasing `CFBundleVersion` sequence: neither a prerelease
label nor a newer publication date permits a downgrade. There is no `/releases/latest`
request, so a repository containing only GitHub prereleases is supported.

After configuring the approved signing material:

1. Keep `MAILSTREAM_UPDATE_PUBLIC_KEY` in `macos/Runner/Configs/AppInfo.xcconfig` equal to
   the `updates` environment's public variable of the same name. The ignored
   `Updates.local.xcconfig` beside it can override public build settings for CI or isolated
   tests. Never put a private key there. CI inherits the feed from the tracked configuration;
   it overrides only the public key and selected channel. The canonical feed is
   `https://github.com/taooceros/mailstream/releases/download/updates/appcast.xml`;
   its xcconfig spelling escapes `//` as `/$()/` so it is not parsed as a comment.
2. Increment `pubspec.yaml`'s build number for **every** update; Sparkle compares
   `CFBundleVersion`, not a commit SHA. Keep build versions increasing, including locally
   installed builds, and never replace the bytes of a published version.
3. Build release and sign with `scripts/sign.sh`, retaining the shared Apple signing team
   `K7HG6KZNNP` and host signing identifier `dev.mailstream.Mailstream`. It signs Sparkle's
   nested helpers inside-out without changing their identifiers.
4. Prepare artifacts from those exact signed bytes:
   `python3 scripts/prepare-update.py "/path/Mailstream Flutter.app" /new/output/directory
   --sparkle-bin /path/to/Sparkle/bin`. The pinned Sparkle distribution is 2.10.1, SHA-256
   `1a856d2a9edb8e628de88121d7be04cf0e2167f8641650b78fca00b14244cf27`.
   Sparkle uses an existing Keychain signing key, or `--key-file /private/path` outside the
   repository. The script never creates keys or publishes anything. It checks the app signature,
   generates and signs the appcast using Sparkle with the bundle's stable/prerelease channel,
   verifies both signatures, verifies the archive against the app's public key, and emits
   the versioned zip, signed `appcast.xml`, and a byte-length/SHA-256/revision/channel manifest.
5. Publish to this repository's `updates` GitHub Release, whose feed URL is shown above.
   It is a GitHub **prerelease**; direct asset URLs do not depend on GitHub treating it as
   the latest stable release. Sparkle's item channel controls client eligibility
   independently of the GitHub release flag.
   Only after explicit publication approval, upload the immutable versioned zip first,
   then the validated appcast (replace only the feed). Keep old packages so a client which
   already fetched the previous feed can finish its download. Do not delete/recreate this
   channel the way the unrelated rolling nightly does.

The initial signed feed and build 4 archive have been published and verified at the canonical
HTTPS URLs. Apps installed before feed activation need one manual bootstrap install with
`scripts/install.sh flutter`; the published CI build 4 also already contains the enabled feed.
Subsequent normal builds inherit the same feed. Installing that initial bootstrap is not a
version upgrade by itself, and Sparkle never downgrades a newer locally installed build.

`.github/workflows/prepare-update.yml` is manual, runs **only from `main`**, and **only
prepares artifacts**. Its job references an `updates` environment. The owner must create
that environment, require reviewers, restrict deployments to `main`, and store
`MAILSTREAM_SIGNING_P12`, `MAILSTREAM_SIGNING_P12_PASSWORD` and
`MAILSTREAM_UPDATE_PRIVATE_KEY` there before using it. The YAML reference alone does not
configure GitHub's approval or branch protections. Set the public
`MAILSTREAM_UPDATE_PUBLIC_KEY` variable at environment or repository scope.

Preflight receives only secret-presence booleans; private material is injected only into
the final signing step, written to a temporary CI keychain/files and removed on exit.
Build caches and uploaded artifacts never include that directory. Local credential
export/upload keeps private values out of process arguments. On the protected disposable
CI runner, the standard `security` CLI briefly uses certificate/keychain passwords as
arguments; the signing seed remains a private file, never an argument. Configuring
credentials or publishing remains a separate owner action, not a side effect of merging.
Its `channel` input defaults to `prerelease`; `stable` must be selected explicitly and is
baked into the bundle before signing. The prepare command derives the signed item channel
from that bundle, not a later publication label.

Ed25519 authenticates the appcast (including channel/version metadata) and the downloaded
archive **before extraction**. Signed-feed failures never expire into an unsigned fallback.
Apple signing protects bundle identity and shared Keychain access. The `updates` channel uses
Apple Development signing for self-use and registered development devices (Apple Silicon,
macOS 26+); it is not a Developer ID-notarized general-public distribution. Broader distribution
needs the appropriate Developer ID signing/notarization setup. Once a trust key is shipped,
do not rotate it casually or bypass verification.

Targeted checks: `python3 -m unittest discover -s Tests -p test_update_package.py` exercises
feed/package/channel matching and real Ed25519 rejection of altered bytes/wrong keys. The native
`RunnerTests` cover production configuration rejection, version ordering, channel eligibility
and actual nib menu ownership/actions. `Tests/UpdaterFixture.swift` is a
synthetic AppKit host of the same standard Sparkle updater for isolated real install/relaunch
tests: compile against the pinned framework, copy its framework into the fixture bundle,
give it a unique bundle ID/profile and temporary test key, then sign with the existing identity.
Its loopback HTTP feed is test-only and is rejected by the production app's configuration
policy. Never point it at the user's email store or publish its keys/packages.


The look is macOS 26's Liquid Glass laid out as islands, after the Dia browser: the whole window
is the system's glass (`NSGlassEffectView`, which `macos/Runner/MainFlutterWindow.swift` places
under the transparent Flutter view, through `macos_window_utils`), the sidebar sits on it, and the
list and the conversation are rounded islands floating on it with a gap between them: the
conversation's white, the lists' a shade grayer, a tray their highlighted row lifts off as a white
card (the row under the pointer half as far, lifted rows 4 pt apart). The toolbars' controls float on capsules of real system glass (`mailstream/glass` platform views
under them), the controls over a row on a raised capsule. Buttons, icon buttons, the search and
text fields and spinners are `macos_ui`'s; Material's remaining widgets are themed to match
(system font sizes, accent blue, gray fills, SF Symbols-style icons from `CupertinoIcons`). It
needs macOS 26.

The sidebar shows from 1200 dp wide (a rail below, whose menu button opens it). The list's
island fills the window; from 1000 dp opening a conversation splits it, the conversation's
island beside the list's, and closing it gives the list the width back. Narrower windows slide
the conversation's island over the list's. Either way a two-finger swipe to the right on the
trackpad drags the conversation out and closes it, springing from the fingers' velocity; the
close button and Esc slide it out on the same spring.

Writing mail happens in a compose column, so other mail can be read beside it: ⌘N, the toolbar's
pencil, F (forward) and the inline reply's "move to compose column" button (⌘⇧O) open it at the
window's trailing edge, the sidebar folding to the rail below 1440 dp. Dragging the gap beside it
moves that edge alone (the list's width follows the window); the list and conversation keep two
panes while 700 dp remain for them and slide over each other below that, except with the column
between them, where it stops widening before the conversation would leave. Its title bar closes the draft (⌘W, asking first when something is
written), minimizes it to a capsule in the bottom-right corner, swaps it to the other side of
the conversation, or floats it over the window (dragged by its title, sized from its top-left
corner). Each draft is a tab; they stay in memory, through mailbox and conversation changes,
until sent or discarded. A reply moved there still goes out with `mail.reply`, threaded with the
original quoted by the engine. To, Cc, Bcc and Subject are editable; fields left untouched keep
the engine's reply plan. New messages and forwards use `mail.send`. All compose modes attach
files from the paperclip picker, file drops on the window, or ⌘V (Finder files and copied image
pixels/screenshots). Normal text paste still edits the focused field. Attachments can be removed
before sending and remain with their draft when switching tabs or browsing other mail.

HTML mail is drawn by WebKit: `macos/Runner/MailHtmlView.swift` is a platform view
(`mailstream/html`) that runs none of the mail's scripts, opens links in the browser, loads
remote images without cookies, zooms out a body wider than the column, and reports its
content height so the body scrolls with the conversation.

Creating a WebKit page and loading its HTML holds the main thread for 20–35 ms, so each platform
view is a light host around a page (MS-109). When a reader or fold closes, its page waits idle (at
most eight) and is shown again only for the same account, conversation, message, part (body or
quote) and full HTML; a page never loads other HTML and is never taken from a host still showing
it. Heights carry a per-page number, and the Dart view asks for the latest height at its own
width once it listens, so a late or stale height cannot resize another showing; a page reused at
another width measures again.

HTML DOM parsing, quote traversal and serialization run in a background Dart isolate before
creating the WebKit bodies (MS-87). A shared eight-entry LRU reuses unchanged HTML and shares
in-flight requests; only one parse isolate runs at a time. Main/quoted parts retain the original
head styling and Gmail/Outlook/Thunderbird/Apple quote rules, including keeping pure-quote mail
whole. A refresh retains the mounted body until replacement parts arrive; message keys and
request handles prevent a disposed or superseded request from replacing another selection.
Opening/closing a quote never reparses HTML or creates its WebKit view before expansion.

Each body releases its request when it goes or its HTML changes, and a split every request
released before its turn is skipped, so switching conversations quickly never waits for the
previous one's queued bodies (a running split finishes) (MS-94). A prefetched conversation (the
80 ms hover, a keyboard step in the single-column list) also splits the HTML its reader opens
with (`Reader.openingHtml`), at low priority: readers' requests always go first, a newer prefetch
replaces the queued one, and prefetched parts wait in an LRU of their own until a reader takes
them, so they never push a reader's parts out. Opening a prefetched conversation then draws its
bodies in the first frame instead of a spinner.

`flutter test test/html_parts_test.dart` covers output, caching, replacement/disposal races,
queue skipping and prefetch priority, fold behavior and the height protocol (owner parameters, the
pull, late older heights, views gone before they answer). `flutter run -d macos --release -t test/html_parts_app.dart` opens a synthetic-only
native reader without accounts or private mail. Set `MAILSTREAM_HTML_BENCH_OUT=/tmp/html-parts.json`
when launching that fixture to compare the exact pre-MS-87 synchronous algorithm (a1fc4b3d)
with queued isolate parsing in the same release runtime: 20 alternating-order pairs each for
small and 2,500-row HTML, reporting enqueue/synchronous time, total preparation latency,
maximum 1 ms event-loop heartbeat gap and cache-hit latency. The gap includes scheduling noise;
enqueue time alone is not the total main-thread cost, and isolate latency is not assumed to
beat synchronous parsing. This is a parsing comparison, not the 120 Hz scrolling benchmark.

Conversation changes fade the reader without scaling its native viewport. The scale-in
transition can leave native WebKit content offset relative to the Flutter body card (MS-82).
The HTML, card insets and WebKit sizing stay unchanged.
The reader occupies the pane's full height from its first frame. Delayed messages and native
HTML measurements grow the content inside that viewport instead of recentering the whole page
(MS-102).
`flutter test test/reader_transition_test.dart` checks unscaled conversation fades and stable
page bounds when delayed content grows. For native rendering/selection/scroll/resize checks
without private mail, run
`flutter run -d macos -t test/html_alignment_app.dart`: open either synthetic conversation,
switch between them, scroll the long one, resize the window and close/reopen the reader.

Reader back swipes keep their current position when a new horizontal gesture takes over an
entrance or spring; vertical scrolling does not stop that motion. The live list stays mounted
under the single-pane layer and widens behind the split reader. Neither path scales WebKit,
waits for message loading, nor rebuilds the shell on animation ticks.
Swipe completion removes the old native reader when its owner clears the detail, rather than
trying to remove it before that rebuild. Stable logical `pageId`s let a newly opened page
cancel the old page's dismissal; an ordinary rebuild of the same page keeps that dismissal.
`flutter test test/split_detail_test.dart` covers dismissal, cancellation, interrupted springs,
vertical input, native-detail teardown and reopening during close. While a page can be swiped
away, `SwipeReadiness` draws a frame every 0.8 s (the macOS embedder drops its cached surfaces
after a second without one) and keeps drawing from the moment fingers land on the trackpad until
the swipe moves the page: after a rest the first few frames render two to four times slower, and
a swipe that started with them dropped frames every time (MS-132). `scripts/bench.sh` measures
that on the real app with `BENCH_SCENARIO=reader-swipe` (`ReaderDismissBench` in `lib/bench.dart`).
For private-mail-free native release measurements of cancel/complete pairs, build
`flutter build macos --release -t test/reader_motion_app.dart`, then launch its executable with
`MAILSTREAM_BENCH=reader-dismiss MAILSTREAM_BENCH_OUT=/tmp/reader-motion`. Park that window at
1240×800 on a private 120 Hz display before its 12-second warmup ends. The real shell uses
1,000 synthetic conversations and native WebKit; six short-cancel/long-complete pairs enter
through Flutter's trackpad event dispatch (not physical trackpad hardware). The TSV files
record `FrameTiming` vsync start and max(build, raster) in milliseconds, as in `lib/bench.dart`,
split into continuous gesture/settle spans so idle time is not counted as dropped frames.
Record the display rate and load alongside each run; do not inspect AX or capture screenshots
during timing, as either can disturb composition. Without the environment flag the same
fixture stays open for native visual/interaction checks.

The open reader follows the normal conversation-list updates: a changed message count or latest
date refreshes that conversation's cached bodies and summary, without closing the pane or
clearing the content while it loads. Unchanged threads (including flag/tag-only updates) keep
their cached bodies. Body completions notify the reader alone, and superseded requests cannot
replace a newer thread revision or change the selected conversation.

`flutter test test/reader_refresh_test.dart` covers live arrival in a mounted reader, valid
cache reuse, lazy refresh after prefetch, overlapping answers, conversation switching and
failed refreshes retaining the previous content.

The frame rate meter (`flutter.showFrameRate`, off by default; Settings ▸ Performance or View ▸
Show Frame Rate, ⌥⌘P) floats in the window's bottom leading corner above every sheet. It shows
the rate of frames drawn back to back, from the engine's `FrameTiming`s (a pause at rest is not a
dropped frame), and the slowest frame's max(build, raster) since its last update, each red past the
display's rate or frame budget, dimmed while nothing draws. Release builds report timings about
once a second, so it updates at that pace (at most every 500 ms otherwise). Off, nothing listens
for timings. `flutter test test/frame_rate_test.dart` covers the counting and the switch;
`flutter build macos --release -t test/frame_rate_app.dart` runs the real shell over synthetic
mail with the setting kept in memory, for screenshots.

Keys: ↑/↓ or J/K move (beside an open conversation they open the next one), Return or Space
opens, Esc or ⌘[ goes back, ⌘W closes the open conversation or chat space, E archives, ⌫ trashes, S stars, U toggles read, D resolves "Waiting on you" (or puts it back), R replies (⇧R or
A replies to all), F forwards, ⌘N writes a new message, ⌘F searches, ⌘R refreshes, ⌘, opens Settings, ⌥⌘P shows or hides the frame rate. In the compose column
⌘Return sends, ⌘V with files or images on the clipboard attaches them, Esc hands the
keyboard back to the list and conversation (closing the draft when nothing is written), and ⌘W
closes the draft (asking first when something is written). On Windows each ⌘ is Ctrl.

Not here: drafts kept on the server or across restarts; in Chat, threads, reactions, editing and
attachments on send.
