# Mailstream Flutter UI

A Flutter desktop front end for Mailstream (macOS, and Windows: see [Windows](#windows)), styled after macOS 26's Liquid Glass with Dia's islands. The Mailstream engine
(accounts, OAuth, sync, push, the cache, threading and AI tagging) runs inside this app's
process: `packages/mailstream` is the Dart binding of the `FFI/` crate (generated by
uniffi-dart), and its build hook bundles `libmailstream.dylib`, which holds the Rust engine (`Engine/`).
The app also carries the `mailstream` command line in `Contents/MacOS` (the Xcode build copies
`FFI/target/release/mailstream`, which `ffi.py` builds); it starts this app when no front end runs.
Beside it is `mailstream-apple-tagger` (`FFI/target/release/`, also built by `ffi.py`), which
the engine runs to tag with Apple Intelligence when `aiTagging.backend` is `apple`.
The UI lists accounts, mailboxes and conversations, reads previews, sender avatars and
messages (with their HTML), searches, marks, archives, trashes, tags, replies and sends new mail through it,
does Google Chat (the spaces of every chat account, their messages, sending and starting new
chats), shows every account's calendar events (an agenda under the week's strip, with the meeting
about to start and its Join on top, day and week timelines with paging and
Today, and each event's details; keys `a`/`d`/`w`, `t`, `←`/`→`), adds events (also by clicking
an empty time in the day or week view)
and changes or deletes the ones the account organizes (New event, ⌘N; Edit and Delete on an
event), answers meeting invitations in mail (a card in the reader with Accept, Tentative and Decline)
and in the calendar (Going, Maybe and Decline on an unanswered invitation's agenda row and in every
invitation's details), manages
accounts and settings, and follows the engine's change events instead of polling.
Mailstream.app need not run.

```sh
# at the repository root: the release engine, command line and Dart bindings (packages/mailstream/lib/src, not committed)
CONFIG=release DART_OUT=$PWD/Flutter/packages/mailstream/lib/src python3 scripts/ffi.py
cd Flutter
flutter test                              # targeted/unit tests (header padding allows install_name rewriting)
flutter build macos --release           # build/macos/Build/Products/Release/Mailstream Flutter.app
../scripts/sign.sh "build/macos/Build/Products/Release/Mailstream Flutter.app"
```

Signing with the app's identifier and team lets the engine read the sign-ins Mailstream keeps
in the Keychain. The build is arm64 only. The app is not sandboxed.

## Windows

`windows/` is the Windows x64 runner. The same Dart UI runs there; `lib/platform.dart` (`Host`)
holds every place the two desktops differ, and the Mac's behavior is unchanged. The engine is
the same Rust one, as `mailstream.dll` beside the executable (the build hook bundles
`FFI/target/release/mailstream.dll`; its Windows specifics are in the root README's FFI section).
The built-in OAuth clients and push settings come from a `config.json` placed beside
`mailstream_ui.exe` (nothing commits or writes one); without it the app has neither, as an
unconfigured Mac build. Build on Windows with Rust (MSVC), Flutter and Visual Studio 2022's
"Desktop development with C++" workload (MSVC, the Windows SDK, C++ CMake tools):

```sh
# at the repository root, in Git Bash (in cmd: set the two variables with `set`, then `python scripts\ffi.py`)
CONFIG=release DART_OUT=$PWD/Flutter/packages/mailstream/lib/src python scripts/ffi.py
cd Flutter && flutter build windows --release   # build/windows/x64/runner/Release/mailstream_ui.exe
```

Without the "C++ CMake tools" component (installing it takes the Visual Studio Installer, as
administrator), `flutter build windows` stops at "Unable to find suitable Visual Studio
toolchain" after writing `windows/flutter/ephemeral/generated_config.cmake`. Any CMake 3.14 or
newer then runs the two steps it would:

```sh
cmake -S windows -B build/windows/x64 -G "Visual Studio 17 2022" -A x64 -DFLUTTER_TARGET_PLATFORM=windows-x64
cmake --build build/windows/x64 --config Release --target INSTALL
```

Flutter links plugins with symbolic links, which need Windows' Developer Mode; without it,
junctions made by hand in `windows/flutter/ephemeral/.plugin_symlinks` (`mklink /J <plugin>
<its folder in the pub cache>`, as `.flutter-plugins-dependencies` lists them) work too.

The GitHub Actions `Windows` workflow builds it, starts the app and keeps a screenshot and the
zipped Release folder as artifacts. On Windows:

- Window: the system title bar moves, maximizes and closes the window (`WindowDragArea` does
  nothing there, and no `macos_window_utils` call is made). The window opens at 1240×800,
  centered, titled Mailstream, no smaller than 820×520. There is no system glass under the
  Flutter view: the window is painted `MailColors.window`. Everything drawn on the window
  (islands, toolbar `GlassCapsule`s, controls) is the same as on the Mac.
- Keys: every ⌘ shortcut is Ctrl (Ctrl+N, Ctrl+F, Ctrl+R, Ctrl+W, Ctrl+[, Ctrl+Enter sends,
  Ctrl+Shift+O), and Ctrl+, opens Settings, as the Mac's app menu does. Ctrl with Alt (AltGr) is
  never a command. Tooltips name the keys of the desktop they run on (`Host.shortcut`).
- Attachments: `windows/runner/window_channels.cpp` implements the `mailstream/files` channel
  the Mac's `MainFlutterWindow.swift` does: the paperclip opens the system's multi-select open
  dialog; files dragged from Explorer onto the window attach (the column shows its drop target
  while they hover); Ctrl+V attaches copied files, else copied image pixels or a screenshot
  (the clipboard's PNG, else its bitmap through WIC, written to a temporary
  `Mailstream-pasted-….png`). A clipboard holding text pastes the text, even when a picture of it
  comes along (spreadsheet cells). Folders are not attached.
- Opening attachments and links: the runner's `mailstream/shell` channel opens them with the
  shell's default verb (`ShellExecuteW`), as Explorer's double-click and the browser do.
- Chat videos play in the log through `video_player_win` (Media Foundation), the Windows
  implementation of `video_player`.
- HTML mail is drawn by WebView2 through `webview_plus` (`WindowsMailHtml` in
  `lib/ui/mail_html_windows.dart`), composed into a Flutter texture as tall as the page, so it
  scrolls with the conversation; quoted history folds as on the Mac. The mail's scripts are off
  (`javaScriptEnabled: false`, WebView2's `IsScriptEnabled`); the app measures the page through
  `ExecuteScript`, which that switch does not stop. Each body is a file in
  `%TEMP%\mailstream-html` (WebView2 gives strings no base URL, so the `file://` inline images in
  the cache would not load), deleted with its view. Links (`target="_blank"` removed first) open
  in the default browser; remote images load in an InPrivate profile. Pages taller than the
  16384 px texture limit stop there and scroll inside. WebView2 Runtime ships with Windows 11.
  `packages/webview_plus` is upstream 0.9.5 with only its Windows implementation declared, so
  the Mac build carries none of it (upstream's macOS Swift package does not resolve under
  Flutter's Swift Package Manager integration).

`flutter test test/windows_platform_test.dart test/compose_paste_test.dart` checks the Windows
branches on any host (`Host.debugMacOverride`): shortcut labels and bindings, AltGr, the drawn
capsule, the title bar area, the WebView2 body and the Ctrl+V attachment paste.

## Application updates (macOS)

The application menu contains **Check for Updates…** and **Automatically Check for
Updates**. Sparkle 2.10.1 owns scheduling, progress, errors, authenticated installation and
relaunch. Checks do not start mail sync. The app checks hourly (`SUScheduledCheckInterval`)
and downloads and verifies a new build in the background without asking; it is installed
when the app quits (or at once from **Check for Updates…**). System profiling is disabled.
Both preferences are Sparkle's own, persisted per user (the menu item turns checking off).

The approved production Ed25519 public key and canonical HTTPS feed are configured in
`macos/Runner/Configs/AppInfo.xcconfig`. The signed feed is published in the repository's
[`updates` prerelease](https://github.com/taooceros/mailstream/releases/tag/updates),
independently of the ad-hoc `nightly` DMGs.

Current builds explicitly opt into `prerelease` through `MAILSTREAM_UPDATE_CHANNEL`.
Sparkle accepts signed appcast items tagged `prerelease` (and ordinary stable items).
A `stable` build only accepts untagged stable items; it does not silently opt into previews.
Both use one monotonically increasing `CFBundleVersion` sequence: neither a prerelease
label nor a newer publication date permits a downgrade. There is no `/releases/latest`
request, so a repository containing only GitHub prereleases is supported.

Every push to `main` that changes the app (`Flutter/`, `Engine/`, `FFI/` or the update
scripts) runs `.github/workflows/publish-update.yml`, which builds, signs and publishes the
update without approval. It runs **only from `main`**, one run at a time, in its `updates`
environment, which admits `main` only and holds `MAILSTREAM_SIGNING_P12`,
`MAILSTREAM_SIGNING_P12_PASSWORD` and `MAILSTREAM_UPDATE_PRIVATE_KEY`; the public
`MAILSTREAM_UPDATE_PUBLIC_KEY` is a repository variable. Its steps:

1. Keep `MAILSTREAM_UPDATE_PUBLIC_KEY` in `macos/Runner/Configs/AppInfo.xcconfig` equal to
   that variable. The ignored `Updates.local.xcconfig` beside it can override public build
   settings for CI or isolated tests. Never put a private key there. CI inherits the feed from
   the tracked configuration; it overrides only the public key and selected channel. The
   canonical feed is
   `https://github.com/taooceros/mailstream/releases/download/updates/appcast.xml`;
   its xcconfig spelling escapes `//` as `/$()/` so it is not parsed as a comment.
2. `python3 scripts/publish-update.py next-version` picks the build number: one past both the
   newest published build and `pubspec.yaml`'s (what `scripts/install.sh` builds locally).
   Sparkle compares `CFBundleVersion`, not a commit SHA, so every update gets a larger one
   and a local install is replaced by the next published build.
3. The release build is signed with `scripts/sign.sh`, retaining the shared Apple signing team
   `K7HG6KZNNP` and host signing identifier `dev.mailstream.Mailstream`. It signs Sparkle's
   nested helpers inside-out without changing their identifiers.
4. `python3 scripts/prepare-update.py "/path/Mailstream Flutter.app" /new/output/directory
   --sparkle-bin /path/to/Sparkle/bin` prepares artifacts from those exact signed bytes. The
   pinned Sparkle distribution is 2.10.1, SHA-256
   `1a856d2a9edb8e628de88121d7be04cf0e2167f8641650b78fca00b14244cf27`.
   Sparkle uses an existing Keychain signing key, or `--key-file /private/path` outside the
   repository. The script never creates keys or publishes anything. It checks the app signature,
   generates and signs the appcast using Sparkle with the bundle's stable/prerelease channel,
   verifies both signatures, verifies the archive against the app's public key, and emits
   the versioned zip, signed `appcast.xml`, and a byte-length/SHA-256/revision/channel manifest.
5. `python3 scripts/publish-update.py publish /that/directory` refuses a build that is not
   newer than every published one, uploads the immutable versioned zip first, then replaces
   the appcast, checks the uploaded appcast byte for byte, and deletes all but the newest five
   archives (a client that already fetched an earlier feed can still finish its download).
   The `updates` release is a GitHub **prerelease**; direct asset URLs do not depend on GitHub
   treating it as the latest stable release, and Sparkle's item channel controls client
   eligibility. Do not delete/recreate it the way the unrelated rolling nightly is.

The OAuth clients and push relay settings (`scripts/app-config.sh`) must not be in a public
package, so updates carry none of them: the engine reads them from
`~/Library/Application Support/Mailstream/config.json`, which `scripts/install.sh flutter`
writes. Install once with it on a new Mac; Sparkle keeps the app current from then on.

Preflight receives only secret-presence booleans; private material is injected only into
the signing step, written to a temporary CI keychain/files and removed on exit. Build caches
and uploaded artifacts never include that directory. The release token is given only to the
steps that read and publish the release, not left in the checkout for the build's tools. On
the disposable CI runner, the standard `security` CLI briefly uses certificate/keychain
passwords as arguments; the signing seed remains a private file, never an argument. A manual
run's `channel` input defaults to `prerelease`; `stable` must be selected explicitly and is
baked into the bundle before signing. The prepare command derives the signed item channel
from that bundle, not a later publication label.

Ed25519 authenticates the appcast (including channel/version metadata) and the downloaded
archive **before extraction**. Signed-feed failures never expire into an unsigned fallback.
Apple signing protects bundle identity and shared Keychain access. The `updates` channel uses
Apple Development signing for self-use and registered development devices (Apple Silicon,
macOS 26+); it is not a Developer ID-notarized general-public distribution. Broader distribution
needs the appropriate Developer ID signing/notarization setup. Once a trust key is shipped,
do not rotate it casually or bypass verification.

Targeted checks: `python3 -m unittest discover -s Tests -p test_update_package.py` exercises
feed/package/channel matching and real Ed25519 rejection of altered bytes/wrong keys. The native
`RunnerTests` cover production configuration rejection, version ordering, channel eligibility
and actual nib menu ownership/actions. `Tests/UpdaterFixture.swift` is a
synthetic AppKit host of the same standard Sparkle updater for isolated real install/relaunch
tests: compile against the pinned framework, copy its framework into the fixture bundle,
give it a unique bundle ID/profile and temporary test key, then sign with the existing identity.
Its loopback HTTP feed is test-only and is rejected by the production app's configuration
policy. Never point it at the user's email store or publish its keys/packages.


The look is macOS 26's Liquid Glass laid out as islands, after the Dia browser: the whole window
is the system's glass (`NSGlassEffectView`, which `macos/Runner/MainFlutterWindow.swift` places
under the transparent Flutter view, through `macos_window_utils`), the sidebar sits on it, and the
list and the conversation are rounded islands floating on it with a gap between them: the
conversation's white, the lists' a shade grayer, a tray their highlighted row lifts off as a white
card (the row under the pointer half as far, lifted rows 4 pt apart). The toolbars' controls
float on capsules Flutter draws (an opaque `MailColors.capsule` face, a hairline rim; no backdrop
blur, which cost every frame of a swipe, MS-187), the controls over a row on a raised capsule.
Only the window's glass is the system's: everything on it is the app's own and looks the same on
Windows (MS-182). Colors,
radii, spacing, elevations, icon sizes and text roles are tokens in `lib/ui/design.dart`; use
them rather than literals. The controls are the app's own, drawn from those tokens in
`lib/ui/controls.dart` (MS-193): buttons (primary, secondary, destructive, plain; small, regular,
large), icon buttons, a segmented control, text and search fields, menu buttons, a date button,
a switch, a checkbox and a confirmation sheet; use them rather than `macos_ui`'s or Cupertino's.
Text editing inside the fields and tooltips are still `macos_ui`'s, which Flutter draws the same
on both platforms. Icons are `CupertinoIcons`. It needs macOS 26.

Small print has two shapes (`lib/ui/common.dart`, MS-190): a `Pill` (22 pt) for things you act on
or that name a thing (recipients, attachments, an event's calendar), and a `Tag` for words that
only describe (a topic, a bundle's count, an invitation's answer, an event's call): 10 pt
semibold in its color on a 12% wash, fully round, 18 pt or 16 pt (`TagMetrics`). Accounts,
calendars and topics are marked by a 6 pt dot of their color (`MarkDot`, `MarkMetrics.dot`), never
a bar or a square. Unread is an accent dot before the avatar in the mail and chat lists alike
(`UnreadDot`), the date staying gray; counts are gray, the rail's on a neutral capsule, red being
kept for errors. `flutter test test/marks_test.dart` covers them.

People have one avatar (`PersonAvatar` in `lib/ui/common.dart`, MS-192), the web reader's look:
their picture, else their initial in one of the 11 system hues on a 15% wash of it
(`MailColors.avatarHue`, `AvatarMetrics`), the hue picked from the lowercased address as the native
app's `Avatar.color` picks it. Senders, Chat people and spaces (a group glyph when a space has no
picture), calendar guests (ringed in the card's color where they overlap) and the accounts in
Settings all use it; only Smart Inbox bundles keep their category glyph (`IconAvatar`). `flutter
test test/avatars_test.dart` covers it.

The sidebar shows from 1200 dp wide (a rail below, whose menu button opens it). The list's
island fills the window; from 1000 dp opening a conversation splits it, the conversation's
island beside the list's, and closing it gives the list the width back. Narrower windows slide
the conversation's island over the list's. Either way a two-finger swipe to the right on the
trackpad drags the conversation out and closes it, springing from the fingers' velocity; the
close button and Esc slide it out on the same spring.

Writing mail happens in a compose column, so other mail can be read beside it: ⌘N, the toolbar's
pencil, F (forward) and the inline reply's "move to compose column" button (⌘⇧O) open it at the
window's trailing edge, the sidebar folding to the rail below 1440 dp. Dragging the gap beside it
moves that edge alone (the list's width follows the window); the list and conversation keep two
panes while 700 dp remain for them and slide over each other below that, except with the column
between them, where it stops widening before the conversation would leave. Its title bar closes the draft (⌘W, asking first when something is
written), minimizes it to a capsule in the bottom-right corner, swaps it to the other side of
the conversation, or floats it over the window (dragged by its title, sized from its top-left
corner). Each draft is a tab; they stay in memory, through mailbox and conversation changes,
until sent or discarded. A reply moved there still goes out with `mail.reply`, threaded with the
original quoted by the engine. To, Cc, Bcc and Subject are editable; fields left untouched keep
the engine's reply plan. New messages and forwards use `mail.send`. All compose modes attach
files from the paperclip picker, file drops on the window, or ⌘V (Finder files and copied image
pixels/screenshots). Normal text paste still edits the focused field. Attachments can be removed
before sending and remain with their draft when switching tabs or browsing other mail.

HTML mail on the Mac is drawn by Blitz (in Rust, below) unless the reader's switch (beside the
header's chips, "Renderer:" Blitz / WebView (original)) picks the WebView (MS-138, MS-147,
MS-166). Every launch starts in Blitz (`MAILSTREAM_READER_RENDERER=webKit` starts in the WebView,
for `scripts/bench.sh`); the choice holds until the app quits and nothing changes it but the
switch: a body a renderer draws poorly never falls back to another by itself. Switching keeps the
message, its open quote and the parts cache; only the chosen renderer's bodies are mounted. The
experimental HyperRender reader (in Flutter, set aside in MS-171) was removed in MS-196, with its
vendored core; a `hyper` renderer name now starts in Blitz.

Blitz (`blitz-dom`/`blitz-html`/`blitz-paint`, `FFI/src/html_page.rs`; `lib/ui/blitz_body.dart`)
parses, lays out and paints each body on a thread of its own in the engine's library; Flutter
only shows the 512-point tiles near the viewport. Iframes, objects and embeds are removed before
any fetch. A body reads what WebKit's view does, anonymously: `data:` and `https:` raster images,
`https:` stylesheets (linked, plus one level of `@import`) and the `https:`/`data:` web fonts they
name; SVG and `file:`/`http:` resources are never loaded, nor are relative and protocol-relative
URLs (`logo.png`, `//host/…`), as in WebKit's view. Web fonts never hold a body back (MS-164): it
draws in system fonts at once and lays out again as each font arrives, unless the font comes over
3 s after the body was shown, when it is only cached for the next open. Only font files whose
`unicode-range` covers some of the body's text are read, at most 8 per body (2 MB each, 512 KB per
stylesheet), and each body registers its fonts in a copy of its own of the system font
collection, so one mail's font never changes another's. Stylesheets and fonts are kept for as long
as their answers allow (a day when they don't say) in
`~/Library/Caches/dev.mailstream.Mailstream/reader-resources` (50 MB, least recently used out
first) and in memory, so a body opened again reads nothing from the network. Requests carry
Safari's user agent: Google Fonts splits its fonts by `unicode-range` only for browsers it knows.
To check it without private mail, run `flutter run -d macos -t test/html_web_font_app.dart` (it
reads Google Fonts; launch with another `HOME` for an empty cache): its first mail's title shows
in the system font, then turns to Lobster, and the second mail, which names Lobster without
linking it, stays in the system font.
Clicked links go through the same check as in the other renderers; a drag selects and ⌘C copies.
Screen readers get the body's text only (Blitz's AccessKit tree is not bridged).
A body Blitz panics on stays blank by itself; every other body keeps drawing (MS-161). Blitz maps
no legacy `background` attribute, which Outlook-style mail (Zillow's listing photos) puts its
pictures in, so the page turns each one on `body`/`table`/`tr`/`td`/`th` into a zero-specificity
`background-image` rule ahead of the mail's own styles, which still win over it (MS-162). To check
it without private mail, run `flutter run -d macos -t test/html_background_app.dart` and open its
one conversation: the listing card shows a sky-over-grass picture, not a gray box. Blitz makes
no anonymous table boxes and dropped a row's children that aren't cells, such as the `<th>`s that
Zillow's phone styles (`@media (max-width: 600px)`) turn into blocks, so its "Other rentals" cards
were empty at 600 points or narrower; the page now wraps each run of such children in a cell (and
a row, under a table or row group) of its own, as CSS's anonymous boxes do, and undoes it when
the width makes them cells again (MS-165). In the same test mail, at a reader narrower than 600
points the "Other rentals" card stacks its picture over its text. Known Blitz gap: an image URL
Blitz can't resolve (`<img src="http://">`) leaves that body blank.

Preparation (`prepareMailImages` in `lib/ui/mail_resources.dart`) is Blitz's image policy: inline
parts (`file://` copies under Mailstream's `messages-v2` cache, canonical paths only, raster bytes
checked) become data URLs, and images that are not HTTPS or raster data are removed; mail without
images goes through as it came. Prepared and split HTML is written back with the doctype the
mail wrote (`documentHtml`): package:html drops a doctype's PUBLIC/SYSTEM keyword, which put
XHTML and HTML 4 newsletters into quirks mode (MS-160).
Links open through the runner's `MailLink` (HTTP(S) with a host, or mailto), in every renderer.

The WebView is `macos/Runner/MailHtmlView.swift`, a platform view (`mailstream/html`). It gets
the mail as the engine gave it, not the prepared parts (MS-167): `webKitDocument` makes two
string edits and parses nothing. It puts a content policy (HTTPS, data and `mscid:` resources
only) ahead of everything but a leading doctype, and readdresses the inline cache's `file://`
folder URL to `mscid://<message>/<part>`, which the page's `InlinePartHandler` serves: only
canonical files inside the inline cache, at most 20 MB, whose bytes are PNG, JPEG, GIF or WebP
(the rule preparation reads them by). So the page keeps the mail's doctype, Outlook's
conditional comments and `srcset`; an http image or an unresolved `cid:` stays blocked by the
policy instead of being removed. The view runs none of the mail's scripts, has no base URL,
allows only its own first load (no redirects, frames or meta refreshes), loads remote images
without cookies, zooms out a body wider than the column, and reports its content height so the
body scrolls with the conversation. Every view talks over the one channel `mailstream/html`, its
calls carrying the view id (a channel per view stayed registered in the engine after the view
went, MS-154). The app's script in the page hides quoted history (the same Gmail, Outlook,
Thunderbird and Apple Mail markup the split cuts out, mail that is nothing but quotes shown whole)
and reports whether it found any with each height; the reader then shows the "…" toggle under
the page, which opens the quotes in place (`fold`), with a rule at their left. Dark mode is the
white card the reader draws around every HTML body, as before. Its `html` and `body` are as
tall as their content (`height: fit-content`): in quirks mode an `auto` height stretched them to
the view, so the page grew by a point with each height it reported, or kept a gap under the mail
after the window was resized (MS-78, MS-160). A body wider than the column zooms out once per
measurement, in the page's script, as the native reader's frames do: `html` is pinned to a width
in pixels (the view's, or for content that needs more, such as a 600 or 900 px newsletter, its
own minimum, `min-content`), measured there, and given a CSS `zoom` of the view's width over the
content's (down to 30%); the height is measured zoomed (zoomed text keeps WebKit's minimum font
size, so it is more than the unzoomed height times the zoom). The zoom never changes the
width the page lays out at. It used to: the view's `pageZoom` widened the page, so content as
wide as the view plus a share of it (a web editor's `width: 100.775%` table) overflowed again
after every step out and the page shrank to the 30% floor, unreadable (MS-183); now such a page
zooms out by that share once. `RunnerTests`' `MailHtmlZoomTests` check it in real pages
(`xcodebuild test -workspace macos/Runner.xcworkspace -scheme Runner
-only-testing:RunnerTests/MailHtmlZoomTests FLUTTER_TARGET=test/html_zoom_app.dart`, after a
`flutter build macos --debug -t test/html_zoom_app.dart`, so the test host runs synthetic mail).
For checks without private mail, run
`MAILSTREAM_READER_RENDERER=webKit flutter run -d macos -t test/html_zoom_app.dart`: open each
of its four synthetic mails, resize the window back and forth; the three 900 px ones stay fully
visible and as tall as their content, and the one with a 100.775% table stays readable at about
full size, its whole table in view.
`MAILSTREAM_READER_RENDERER=webKit flutter run -d
macos -t test/html_webkit_app.dart` shows quotes that fold, an inline image (a synthetic PNG it
writes to the inline cache's folder `f167…`), a `srcset` image and a forward that is all quote.

Creating a WebKit page and loading its HTML holds the main thread for 20–35 ms, so each platform
view is a light host around a page (MS-109). When a reader closes, its page waits idle and is
shown again only for the same account, conversation, message and full HTML; a page never loads
other HTML and is never taken from a host still showing it, and it opens or closes its quotes as
the reader's fold is when shown again. Heights carry a per-page number, and the Dart view asks
for the latest height at its own width once it listens, so a late or stale height cannot resize
another showing; a page reused at another width measures again.

An idle page keeps its own WebContent process and the images it decoded, up to hundreds of MB for
a newsletter, so idle pages close after a minute, past eight, or once their processes together
use more than 200 MB (oldest first; the most recently closed reader's page stays) (MS-155).
WebKit ends a closed page's process by leaving it to exit by itself, which a background process
on a busy machine did not get to do, so every closed page kept its process (MS-153); the pool
kills the process of each page it lets go, once WebKit has closed the page.

For Blitz, HTML DOM parsing, quote traversal and serialization run in a
background Dart isolate before the bodies show (MS-87). A shared eight-entry LRU reuses unchanged
HTML and shares in-flight requests; only one parse isolate runs at a time. Main/quoted parts
retain the original head styling and Gmail/Outlook/Thunderbird/Apple quote rules, including
keeping pure-quote mail whole. A refresh retains the mounted body until replacement parts arrive;
message keys and request handles prevent a disposed or superseded request from replacing another
selection. Opening/closing a quote never reparses HTML. The WebKit body waits for none of this:
it asks for no parts (a request queued when the switch moves to WebKit is let go), and prefetch
splits nothing while it is chosen.

Each body releases its request when it goes or its HTML changes, and a split every request
released before its turn is skipped, so switching conversations quickly never waits for the
previous one's queued bodies (a running split finishes) (MS-94). A prefetched conversation (the
80 ms hover, a keyboard step in the single-column list) also splits the HTML its reader opens
with (`Reader.openingHtml`), at low priority: readers' requests always go first, a newer prefetch
replaces the queued one, and prefetched parts wait in an LRU of their own until a reader takes
them, so they never push a reader's parts out. Opening a prefetched conversation then draws its
bodies in the first frame instead of a spinner.

`flutter test test/mail_resources_test.dart` covers the resource policy and the renderer
switch; `test/html_parts_test.dart` output, caching, replacement/disposal races,
queue skipping and prefetch priority, fold behavior, the WebKit page's HTML (the engine's but for
the policy and inline image addresses) and its fold, and the height protocol (owner parameters, the
pull, late older heights, views gone before they answer). `flutter build macos --release -t
test/html_open_app.dart`, launched with `MAILSTREAM_HTML_OPEN_OUT=/tmp/open.json`, times how long
a WebKit body takes to open (mount to first reported height) for four synthetic mails (4, 22, 65
and 300 KB) one at a time and all at once (MS-167). `flutter run -d macos --release -t test/html_parts_app.dart` opens a synthetic-only
native reader without accounts or private mail. Set `MAILSTREAM_HTML_BENCH_OUT=/tmp/html-parts.json`
when launching that fixture to compare the exact pre-MS-87 synchronous algorithm (a1fc4b3d)
with queued isolate parsing in the same release runtime: 20 alternating-order pairs each for
small and 2,500-row HTML, reporting enqueue/synchronous time, total preparation latency,
maximum 1 ms event-loop heartbeat gap and cache-hit latency. The gap includes scheduling noise;
enqueue time alone is not the total main-thread cost, and isolate latency is not assumed to
beat synchronous parsing. This is a parsing comparison, not the 120 Hz scrolling benchmark.

Conversation changes fade the reader without scaling its native viewport. The scale-in
transition can leave native WebKit content offset relative to the Flutter body card (MS-82).
The HTML, card insets and WebKit sizing stay unchanged.
The reader occupies the pane's full height from its first frame. Delayed messages and native
HTML measurements grow the content inside that viewport instead of recentering the whole page
(MS-102).

Reader back swipes keep their current position when a new horizontal gesture takes over an
entrance or spring; vertical scrolling does not stop that motion. The live list stays mounted
under the single-pane layer and widens behind the split reader. Neither path scales WebKit,
waits for message loading, nor rebuilds the shell on animation ticks.

The open reader follows the normal conversation-list updates: a changed message count or latest
date refreshes that conversation's cached bodies and summary, without closing the pane or
clearing the content while it loads. Unchanged threads (including flag/tag-only updates) keep
their cached bodies. Body completions notify the reader alone, and superseded requests cannot
replace a newer thread revision or change the selected conversation. The state keeps the bodies
of the 32 most recently opened or prefetched conversations (`MailState.keptThreads`) plus the
open one, any a reader still draws and any still loading; older ones are dropped and reopening
one asks the engine again, whose body cache answers it.

The frame rate meter (`flutter.showFrameRate`, off by default; Settings ▸ Performance or View ▸
Show Frame Rate, ⌥⌘P) floats in the window's bottom leading corner above every sheet. It shows
the rate of frames drawn back to back, from the engine's `FrameTiming`s (a pause at rest is not a
dropped frame), and the slowest frame's max(build, raster) since its last update, each red past the
display's rate or frame budget, dimmed while nothing draws. Release builds report timings about
once a second, so it updates at that pace (at most every 500 ms otherwise). Off, nothing listens
for timings. `flutter test test/frame_rate_test.dart` covers the counting and the switch;
`flutter build macos --release -t test/frame_rate_app.dart` runs the real shell over synthetic
mail with the setting kept in memory, for screenshots.

The agenda (`lib/ui/calendar.dart`, MS-169) lists each day's events as rows: a time column in
tabular figures, the calendar's 6 pt dot, title and place, the guests' avatars, or Going, Maybe
and Decline while the account has not answered. Above it, this week's days (today raised, a

The calendar moves like the reader (`lib/ui/calendar_grid.dart`, MS-170). Two fingers on the
trackpad drag the day or week view's days 1:1, the hours in the gutter staying put; past a third
of the width or flicked they spring on to the next day or week on `Motion.spring`, else back. ←
and → (and the arrows in the bar) slide the next one in over `Motion.page`. The days either side
are laid out at rest, after the first frame in which nothing animates, each in layers of its own,
so paging only moves layers. Agenda, Day and Week fade and grow into each other over
`Motion.short` under a capsule that slides to the view picked, and Day and Week keep the hours
the other was scrolled to. ↑ and ↓ (J and K in the agenda) open the next or previous event in
view at once, the list or timeline scrolling it into view and the event's pane fading through
over `Motion.swap`. `flutter test test/calendar_grid_test.dart` covers the swipe, the slide, the
kept hours and the order ↑ and ↓ follow.
